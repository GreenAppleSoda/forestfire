# 웹 초기 로딩 성능 최적화 보고서

> 대상: 신입 개발자  
> 목적: 지도 페이지 첫 접속이 느렸던 원인과, 이번 작업에서 무엇을·왜·어떻게 고쳤는지 이해하기  
> 작성 기준일: 2026-07-27

---

## 1. 한 줄 요약

팀원이 `localhost:3000`에 **캐시 없이** 접속하면 약 **8초** 걸리던 문제를 조사했고,

1. **데이터 로딩 경로를 바꿨고** (서버 경유 → 브라우저가 정적 JSON 직접 로드)
2. **JSON 용량을 줄였으며** (중복 제거 + SVG 경로 단순화)
3. **큰 파일은 나중에 받게** 했습니다 (읍면동 지연 로딩)

그 결과 **첫 화면에 꼭 필요한 데이터**가 약 **12.9MB → 약 3.6MB**로 줄었습니다.

---

## 2. 배경: 왜 느렸나?

### 2.1 증상

| 상황 | 체감 |
|------|------|
| 팀원 (캐시 없음, 첫 방문) | 약 8초 로딩 |
| 본인 (브라우저/Next 캐시 있음) | 상대적으로 빠름 |

→ **캐시가 없을 때** 매번 큰 데이터를 처음부터 받는 구조가 문제였습니다.

### 2.2 기존 구조 (느린 경로)

홈 페이지(`frontend/src/app/page.tsx`)가 **서버 컴포넌트**였고, 페이지를 그리기 **전에** Express(`localhost:4000`)로 아래 API를 **전부** 호출했습니다.

- `/api/map/data`
- `/api/map/admin/sido`
- `/api/map/admin/sigungu`
- `/api/map/admin/emd`
- `/api/map/ml-scores`
- `/api/map/daily-risk`

그리고 `cache: "no-store"` 옵션 때문에 **매 요청마다 캐시를 쓰지 않았습니다.**

흐름을 그림으로 보면:

```text
[브라우저] → [Next.js 서버] → [Express] → [디스크에서 JSON 읽기·파싱]
                ↑
        여기서 큰 JSON을 다 받을 때까지
        HTML/화면이 거의 안 나감
```

### 2.3 파일이 얼마나 컸나? (최적화 전)

| 파일 | 대략 크기 | 역할 |
|------|-----------|------|
| `map-data.json` | ~8.3 MB | 산불 이력, 산 정보, 시군구 통계 |
| `admin-emd.json` | ~4.3 MB | 읍면동 SVG 경계 (지역 5040개) |
| `admin-sigungu.json` | ~0.2 MB | 시군구 경계 |
| `admin-sido.json` | ~0.03 MB | 시도 경계 |
| 기타 (ml scores 등) | 작음 | 예측 점수 |

**합계 약 12~13MB**를 첫 진입에 거의 한꺼번에 처리하고 있었습니다.

### 2.4 `map-data.json`이 특히 컸던 이유

용량을 쪼개 보면:

| 항목 | 대략 | 설명 |
|------|------|------|
| `provinces` | ~2.5 MB | `regions`와 **거의 같은 내용이 두 번** |
| `regions` | ~2.5 MB | 시군구 통계 + 산 목록 |
| `mountains` | ~2.4 MB | 산 전체 인덱스 (설명문 `details` 포함) |
| `history` | ~1.0 MB | 산불 이력 |

즉 “지도 선이 세밀해서”만 큰 게 아니라, **같은 데이터를 여러 곳에 중복 저장**한 것도 큰 원인이었습니다.

### 2.5 `admin-emd.json`이 컸던 이유

- 읍면동 **약 5040개**의 SVG path (`d` 문자열)
- `regions`와 내용이 겹치는 `markers` 배열 (~1MB)
- 화면에서 안 쓰는 `fill` 필드 등 중복 필드

> 참고: 초기 화면은 **시도/시군구**만으로도 지도를 그릴 수 있고, 읍면동은 **많이 확대한 뒤**에야 필요합니다.

## 3. 해결 전략 (3단계)

우선순위는 “가장 효과가 큰 것부터”였습니다.

| 단계 | 무엇을 | 왜 |
|------|--------|-----|
| A | 로딩 경로 변경 + 서버 캐시 | 불필요한 서버→서버 hop / 반복 디스크 I/O 제거 |
| B | JSON 자체 압축 | 네트워크·파싱 시간 자체를 줄임 |
| C | 읍면동 지연 로딩 | 첫 페인트를 더 앞당김 |

## 4. 단계 A — 로딩 경로 변경 & Express 캐시

### 4.1 프론트: 정적 파일을 브라우저가 직접 받기

**변경 파일:** `frontend/src/app/page.tsx`

**Before (개념):**

```ts
// 서버에서 Express API를 no-store로 호출 → 큰 props를 클라이언트로 전달
await fetch("http://localhost:4000/api/map/data", { cache: "no-store" });
```

**After (개념):**

```ts
"use client";
// 브라우저가 Next가 서빙하는 public 파일을 직접 fetch
await fetch("/data/map-data.json", { cache: "default" });
```

#### 왜 이게 빠른가?

1. **Next 서버가 Express를 대신 호출하며 기다리는 시간**이 사라짐  
2. 파일은 이미 `frontend/public/data/`에 있으므로 **정적 파일 서빙**이 가능  
3. 브라우저 `cache: "default"` → **두 번째 방문부터 HTTP 캐시**를 활용하기 쉬움  
4. 로딩 중 UI(`지도를 불러오는 중입니다...`)를 먼저 보여줄 수 있음

> `public/data/*.json` 은 URL `/data/*.json` 으로 접근됩니다.  
> 예: `frontend/public/data/map-data.json` → `http://localhost:3000/data/map-data.json`

### 4.2 백엔드: JSON을 매번 디스크에서 읽지 않기

**변경 파일:**

- `backend/src/lib/data.ts` — `readJsonCached()` 추가
- `backend/src/routes/map.ts` — 지도 API가 캐시 함수 사용 + `Cache-Control` 헤더

**아이디어:**

```text
첫 요청: 파일 읽기 → JSON.parse → 메모리에 저장
다음 요청: 파일 수정 시각(mtime)이 같으면 메모리 결과 재사용
파일이 바뀌면: 다시 읽고 캐시 갱신
```

API 응답에 대략 이런 헤더도 붙입니다.

```http
Cache-Control: public, max-age=60, stale-while-revalidate=600
```

> 홈 페이지는 이제 `/data/*.json`을 주로 쓰지만,  
> `HistorySyncControl` 등 **Express `/api/map/*` 를 쓰는 기능**도 빨라지도록 같이 손댔습니다.

## 5. 단계 B — JSON 용량 줄이기

### 5.1 압축 스크립트

**새 파일:** `etl/map/compress_web_data.py`

실행 방법:

```bash
# 프로젝트 루트(ForestFire)에서
python etl/map/compress_web_data.py
```

스크립트가 하는 일:

#### (1) admin 레이어 (`admin-sido/sigungu/emd.json`)

- SVG path에 **Douglas–Peucker** 단순화 재적용 → 점 개수↓, `d` 문자열↓
- 좌표 소수점 자릿수 축소
- 프론트에서 안 쓰는 **`markers` 비우기**
- 중복 필드 **`fill` 제거** (색은 `color` / 런타임 계산으로 충분)
- JSON을 compact 형태(`separators=(",", ":")`)로 저장

#### (2) `map-data.json`

- `provinces` 중복 제거 → `[]` (프론트는 `regions`를 우선 사용)
- 지역별 `catalog_mountains` / `top_mountains`는 **가벼운 필드만** 유지  
  (`id`, `name`, `height`, `fire_count`, 좌표 등)
- 산 상세 `details` 길이 축소
- 이력의 `mountain_list`도 id 위주로 슬림화 (상세는 `mountains` 인덱스로 보강)

### 5.2 압축 결과 (실측)

| 파일 | Before | After | 비율 |
|------|--------|-------|------|
| `admin-emd.json` | 4.32 MB | 2.34 MB | ~54% |
| `admin-sigungu.json` | 0.19 MB | 0.12 MB | ~62% |
| `admin-sido.json` | 0.03 MB | 0.02 MB | ~75% |
| `map-data.json` | 8.29 MB | 3.43 MB | ~41% |
| **합계** | **~12.8 MB** | **~5.9 MB** | **~46%** |

### 5.3 ETL이 다시 커지지 않게 맞춤

데이터를 **다시 생성**해도 예전처럼 비대해지지 않도록 생성 스크립트도 수정했습니다.

| 파일 | 변경 요지 |
|------|-----------|
| `etl/map/build_admin_layers.py` | 단순화 강도↑, markers 미출력, compact JSON |
| `etl/map/export_map_data.py` | `provinces` 중복 제거, 카탈로그 슬림화, details 단축 |
| `etl/map/refresh_history_layers.py` | markers 의존 제거, regions만 roll-up, compact 저장 |

> shapefile로 admin을 다시 만들거나 map-data를 export한 뒤에도,  
> 필요하면 `python etl/map/compress_web_data.py` 를 한 번 더 돌리면 안전합니다.

## 6. 단계 C — 읍면동(emd) 지연 로딩

**변경 파일:** `frontend/src/app/page.tsx`

### 6.1 아이디어

줌 레벨에 따라:

- 낮음 → **시도**
- 중간 → **시군구**
- 높음 → **읍면동**

그런데 기존에는 읍면동(가장 큰 admin 파일)까지 **처음부터** 받았습니다.

### 6.2 지금 로딩 순서

```text
1차 (지도 바로 표시)
  - map-data.json
  - admin-sido.json
  - admin-sigungu.json
  - ml / daily-risk (작은 파일)

2차 (백그라운드)
  - admin-emd.json
```

1차만으로도 지도 UI가 뜨고, emd는 받는 동안 빈 레이어(`EMPTY_EMD`)를 넣어 둡니다.  
고배율로 확대하기 전에 보통 로드가 끝납니다.

### 6.3 체감 효과

| 구분 | 대략 받아야 하는 양 |
|------|---------------------|
| 예전 첫 페인트 | ~12.9 MB |
| 지금 첫 페인트 (emd 제외) | **~3.6 MB** |

→ 같은 네트워크라도 **화면에 지도가 나오기까지** 훨씬 빨라집니다.

```text
[브라우저]
   │
   ├─ 1) /data/map-data.json
   ├─ 2) /data/admin-sido.json
   ├─ 3) /data/admin-sigungu.json
```

예측·동기화 같은 **동적 API**는 여전히 Express / ML 서비스를 사용합니다.  
이번 최적화의 핵심은 **“거의 안 바뀌는 큰 지도 데이터”**입니다.

## 9. 신입이 알아두면 좋은 개념

### 9.1 `public/` vs API

| 방식 | 언제 쓰나 |
|------|-----------|
| `public/data/*.json` | 자주 안 바뀌는 대용량 정적 데이터 |
| Express `/api/...` | 실시간 예측, 동기화, 권한/가공이 필요한 요청 |

### 9.2 서버 컴포넌트에서 큰 JSON을 props로 넘기면?

Next 서버가 JSON을 받은 뒤 **RSC payload**로 클라이언트에 다시 실어 보냅니다.  
데이터가 수 MB면 **전송이 두 번**에 가깝게 커질 수 있습니다.  
그래서 이번엔 **브라우저가 정적 파일을 직접** 받게 바꿨습니다.

### 9.3 Douglas–Peucker란?

꺾은선/다각형에서 **모양은 비슷하게 유지하면서 점을 줄이는** 알고리즘입니다.  
지도 경계를 조금만 부드럽게 만들어도 파일 크기가 크게 줄어듭니다.

### 9.4 왜 `provinces`를 비웠나?

프론트 `KoreaSvgMap`은 이미:

```ts
mapData.regions?.length ? mapData.regions : mapData.provinces
```

처럼 **`regions`를 우선** 사용합니다.  
같은 시군구 배열을 두 번 넣을 필요가 없었습니다.

### 9.5 산 정보가 카탈로그에 짧게만 있어도 되나?

패널에서 산을 열 때 `mountains` 인덱스와 합칩니다.

```ts
// 개념
const full = mountainIndex[m.id] ? { ...mountainIndex[m.id], ...m } : m;
```

그래서 지역별 목록에는 **id/이름/좌표** 정도만 두고,  
긴 설명은 `mountains` 한곳에만 두면 됩니다.

## 10. 직접 확인하는 방법

### 10.1 캐시 없는 첫 방문처럼 테스트

1. 프론트 재시작
   ```bash
   cd frontend
   ```

   또는 DevTools → Network → **Disable cache** 체크 후 새로고침
3. Network 탭에서 `/data/*.json` 크기·소요 시간 확인

### 10.2 Next 빌드 캐시까지 지우고 싶을 때

```powershell
Remove-Item -Recurse -Force frontend\.next
cd frontend
npm run dev
```

### 10.3 JSON을 다시 압축하고 싶을 때

```bash
python etl/map/compress_web_data.py
```

## 11. 앞으로 더 할 수 있는 것 (선택)

이번 범위 밖이지만, 여유 있으면 검토할 만한 항목입니다.

1. **GeoJSON/path를 gzip/brotli**로 미리 압축해 두기 (서버 압축 설정)
2. **시군구만으로 충분한 줌**에서는 emd 요청 자체를 더 늦게 (확대 직전)
3. `map-data`의 `history` / `mountains`를 **지역 클릭 시 부분 로드**
4. SVG 대신 **벡터 타일** 같은 지도 전용 포맷 (구조 변경이 큼)

## 13. 결론

느림의 본질은 “코드가 비효율적인 작은 버그”라기보다,

> **첫 화면에 필요 이상으로 큰 JSON을, 캐시 없이, 서버를 경유해 한꺼번에 받던 구조**

에 가까웠습니다.

이번 작업은 그 구조를

> **가벼운 정적 파일을 브라우저가 받고 → 큰 레이어는 나중에 → 생성 파이프라인도 가볍게**

로 바꿨습니다.  
신입 개발자는 위 체크리스트와 Network 탭의 `/data/*.json` 용량만 봐도,  
최적화가 실제로 먹혔는지 스스로 검증할 수 있습니다.
